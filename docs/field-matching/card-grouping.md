# Ozon 同款 SKU 合并：数据组织与核验状态

更新：2026-10-09。本文记录当前讨论结论，供后续开发读取上下文。内部规则已经实现；正式发布接口、分组结果和全部官方约束尚未完成真实验证。

## 要解决的问题

通过 Ozon 商品发布／更新接口，将同款商品的多个颜色、尺码 SKU 展示在一个商品页面中。每个 SKU 保持独立商品标识，并有自己的变体属性；同款共享“合并至同一张卡片”值。

检索和核验应以业务名称为入口：中文“合并至同一张卡片／合并至一张卡片”、俄文 `Объединить на одной карточке`，以及同款、商品变体、颜色、尺码。先确认业务含义和适用品类，再从真实 Schema 确定属性 ID。不得把当前的 `8292` 当作所有品类通用的检索或执行前提，也不得把其他样例中的 `9048` 直接替换进当前规则。

## 已明确的内部策略与实现

用户明确指定：当前一条 1688 采集商品记录下的全部 SKU 视为同一款，使用同一组字符串。这里指同一条商品记录，不是整个采集批次内的所有商品。

2026-10-09 用户确认解析时为每个产品自动生成唯一的 `value`。沿用下面已实现的源商品标识策略：唯一性按产品划分，同一产品全部 SKU 共用；重复解析同一产品保持原值，不按解析次数重新生成随机值。

- 当前执行范围：Ozon 品类 `200000933`、类型 `93182`。
- 当前字段：属性 `8292`“合并至一张卡片”。
- JSON 规则：类型清单引用 `common.product.card-group`，其中配置 `generator: "source-product-card-key"`。见 [类型字段清单](../../rules/categories/200000933/types/93182.json) 和 [分组字段模块](../../rules/common/product/card-group.json)。
- 分组值：`1688-{源商品 offerId}`；相同源商品重复采集、标题或 SKU 顺序变化不改变它，不同源商品 ID 分开成组。
- 不根据标题、品牌、货号、颜色或尺码猜测分组；当前不跨源商品链接合组。
- 界面作为公共属性显示、确认和导出一次，`scopeKeys=["product"]`、`resolution="generated"`，仍需人工确认。

这是一条人工批准的项目策略，不是 Ozon 规定的命名模板。已经通过的本地行为检查不证明 Ozon 会接受或成功合并。当前正式商品发布功能未实现。

## 参数层级与发布组织思路

必须区分三个层级：

1. **分组值**：同款共享的文本，例如 `1688-925890695648`。
2. **属性对象**：用当前 Schema 对应的属性 ID，将文本放入 `values[].value`。
3. **请求体**：每个 SKU 对应独立商品条目，每条携带自己的属性对象。桌面显示一次公共字段不等于提交时只给一个 SKU 填写。

查到的开源代码将发布／完整更新请求发送到 `/v3/product/import`，将属性更新请求发送到 `/v1/product/attributes/update`。两者以 `items` 组织商品，单条商品内是 `attributes`。同批或分批提交的合并行为尚未通过本项目真实请求验证，不能认为“放在同一数组中”本身就会建立同款关系。

以下仅为当前属性的候选片段，不是完整上架请求或已验证成功的 Payload：

```json
{
  "complex_id": 0,
  "id": 8292,
  "values": [
    {
      "dictionary_value_id": 0,
      "value": "1688-925890695648"
    }
  ]
}
```

已有 [四 SKU 参数草稿](examples/925890695648.card-grouping.request-fragment.json) 仅包含独立 SKU 编号和分组属性，编号沿用项目示例；它不是正式上传入口，不应直接提交。[业务展示示例](examples/925890695648.card-grouping.json) 也是预览材料。

## 后续必须避免的误用

- `dictionaryId` / `dictionary_id` 是字典标识，`dictionary_value_id` 是其中具体选项的标识，不能互填。当前缓存中俄罗斯尺码字典为 `835`，它不是“44码”的值 ID。颜色、尺码、类型、品牌应根据当前 Schema 和字典接口解析，不把字符串样例当作通用可提交值。
- 查到的 v3 请求定义使用 `description_category_id` 和 `type_id`，不是旧示例中的 `category_id`。顶层 `type_id` 与属性 `8229` 不同；不得混用其他品类的 ID。
- 带 `//` 注释的展示示例不是合法 JSON。
- `dictionary_value_id: 0` 有客户端写法依据，但尚未证实是此属性的官方强制要求；也未证实省略它的实际行为。
- 不能把“相同分组值”表述为一定合并成功；“相同颜色和尺码必然报错”“必然生成色块”也未取得已核验响应支持。
- 同组类型、品牌及其他相关属性需要核对一致性，具体规则范围仍需官方依据。不得凭未知业务差异自动合组。
- 不引入父子商品请求对象、专用 `parent_id` 或任意 `complex_id` 作为合并机制，除非取得对应接口／品类依据。

## 待验证事项与继续工作的入口

1. 取得可读取的官方业务说明，确认同组条件以及分组值的字符、长度限制。
2. 刷新当前品类／类型 Schema，核对字段 ID、类型、字典、必填与集合标记。
3. 获取颜色和俄罗斯尺码等实际字典选项，明确源尺码的人工转换方案。
4. 核实发布与属性更新接口的当前请求定义，确认零值／省略字段写法。
5. 在用户明确授权真实写入后，保存真实请求、返回任务、最终处理结果及商品合并结果；仅有 `task_id` 或模拟测试通过不算验证成功。

核验前保留未知项，不把第三方样例、用户提供的思考方案或项目内部分组策略标记为“官方已验证”。本记录不修改现有映射规则、字典规则或 SKU 标识生成策略。
