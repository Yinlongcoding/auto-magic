# 确定性匹配、人工复核与持续学习规划

> 2026-09-28 实现更新：桌面“运行规则匹配”已切换为 JSON 品类/类型规则与人工填写表单。支持中文填写后查询字典、人工选择合法 valueId、保存草稿、类型规则回写、SQLite 版本/审核统计和中断写入恢复。100 次有效审核且正确率 ≥98% 显示可信，低于门槛留空。最新使用与边界见 [规则说明](../../rules/README.md)。下文关于空 C# 规则目录、只读表格、尚无持久化的描述是历史状态。自动模型训练、正式上架和图形化回滚仍未实现。

更新：2026-09-24。本文按本地代码与仓库设计文档核查，不是外部机器学习产品调研。

## 本次生效的需求

1688 事实不能保证覆盖 Ozon 字段和 valueId。运行链路改为：采集与清洗 → 已审核规则 → 字典唯一精确匹配 → 本地合同校验 → 空白待人工项 → 属性草稿。未知标签、缺失证据、冲突、无法确定的字典值、未支持的转换均不得调用 AI/Qwen 补齐；不得把近似候选、默认值或模型置信度当成真实商品值。

`ProductMappingRunner` 不再调用语义模型；旧签名仅保留兼容，API Key 不参与运行。已绑定的字典字段使用原始事实值搜索当前 category/type/attribute 的 Ozon 字典，只接受返回结果中唯一、文本完全相同且 ID 有效的记录。中文与俄文不一致时不会自动翻译或选择第一条候选。查询失败、无精确候选或多个 ID 同文时均留空。字段类型/证据/基数校验失败的确定性建议也留空，保留诊断与来源证据。

待人工项使用 `manual_required`，`values=[]`，因此文本与 valueId 都为空；不把源事实误当成目标答案。源事实在原始事实表与证据中保留。必填和选填均可进入待人工项；必填未解决会阻断提交。SKU 的待人工覆盖会压住公共属性，组合草稿不会重新填入公共值。

桌面新增“运行规则匹配”，展示结果和草稿；保留“生成 AI 输入 JSON”作为本地历史诊断预览，不发送请求。当前结果表仍只读，尚无工人填写、保存、审核或训练闭环。当前默认规则目录为空，因此实际业务字段会全部待人工处理；测试目录中的规则不是生产预置规则。

## 已确认的文件方案与人工纠正规则（待实现）

2026-09-28 再次确认公共属性层：经用户使用 Ozon 官方 API 在多个品类和类型验证，且 attributeId、dictionaryId、valueId 均一致的属性保存到 `rules/common/{module}.json`。当前已提升性别。原产国的 267 条完整 Ozon 官方中俄值已按 valueId 对齐并保存到 `rules/common/catalogs/origin-country.json`，作为目标字典参考；其中重复中文名称保留全部候选，匹配时必须判为歧义。待从 Schema 确认 dictionaryId 后，再建立可执行公共规则。材质、颜色待提供并复核具体配置后加入。加载顺序为 common → `rules/categories/{categoryId}/rules.json` → `types/{typeId}.json`，后层可以完整覆盖或禁用继承规则。未经跨品类验证的值不进入 common。

### 命中即使用，上架人工修正即替换

1. 读取当前有效规则，适用范围与源事实匹配、Schema/字典/类型校验通过时直接使用；没有匹配或存在冲突时留空，不调用 AI/Qwen。
2. 实际上架环节，工人确认保存了对规则自动填写结果的修改后，以人工修正为准，替换本次命中的对应规则或值映射。编辑中、取消编辑或等价值保存不产生替换。触发点是人工确认保存，不以 Ozon 上架成功作为正确性判断；网络、库存等上架错误不是映射纠错。
3. 只修改目标条目：例如在同一适用范围内，“红色 → ID A”被人工改成“红色 → ID B”，只替换该源值对应的映射，不改变蓝色等其他值，也不把整个颜色字段固定为 ID B。只有人工明确纠正了字段关系，才修改字段绑定；只改值不能推断字段关系变化。
4. 替换身份至少包含 categoryId、有效 type 范围、ruleId/mappingId、目标 attribute/dictionary、商品/SKU 作用域与源值条件。当前类型的纠正落到对应 types 文件，替换已有类型条目或覆盖继承的品类条目；不由一次商品操作自动扩展到整个品类或其他类型。明确修改品类规则时才变更品类文件。
5. 保留旧 revision，生成新 revision 并切换当前有效版本；记录人工修改前后值、操作者、时间、源事实和所依据的旧版本。若旧版本已被其他操作更新，先处理冲突，不能静默覆盖新版本。后续相同条件的匹配使用修正版本；既有商品结果不追溯批量改写。
6. 人工修改仍需通过当前目标合同校验。缺失源事实的人工补填只记人工事实，不能形成无条件默认映射；清空目标值表示撤销当前答案，不学习成“所有商品都填空”，应暂停对应命中映射并转人工复核。
7. 人工修正版确认保存后即可作为有效规则使用，无需再等待 100 次校验；“启用状态”和“统计可信状态”分开。旧版本的错误计入旧版本，新版本独立积累审核统计，不直接继承旧版的正确率或 trusted 标记。

示例：品类 123456、类型 100001 的“红色”曾命中 ID A。上架时工人确认改为合法 ID B，系统生成该类型映射的新版本并立即生效。下次该类型同源值使用 B，其他类型和其他颜色不受影响。

这是对旧方案“单次人工修改仅影响当前商品”的明确例外：上架时对规则结果的已确认纠正必须回写并替换对应有效映射。人工编辑、JSON 加载、回写和版本存储尚未实现，本节不表示已有运行能力。

验收场景：命中复用；确认纠正后当前商品与下一次同条件匹配使用新值；其他类型/值不受影响；取消编辑不回写；非法 ID 不激活；重复保存不重复建版本；并发旧版本不覆盖新版本；新版本统计不继承旧分数。当前仅核对文档与场景一致性，运行验收待实现时执行。

## 建议的新学习闭环（规划，尚未启用）

1. 工人填写/纠正目标值，字典属性从当前 Ozon 字典选合法 ID；保存事实快照、目标 Schema 指纹、商品/SKU 作用域、修改前后值、操作者、时间、原因和规则 revision。人工填写缺失事实时必须另记人工来源，不能伪造采集 factId。
2. 区分“保存草稿”与“审核通过”。只有经复核的标签进入学习集；有争议、撤销、无来源或未复核记录不视为正确答案。普通草稿修改仅作用于当前商品；实际上架环节对规则结果的确认纠正，按上节回写替换对应有效规则。
3. 分离字段关系与值映射：标签别名、目标属性与作用域变化产生 TypeMappingProfile revision；同字段的新颜色/材质形成 ValueMappingCache 候选；已有命中值被上架人工纠正时，直接产生替换用的新版本。值缓存按租户、数据源、category/type、attribute/dictionary、规范化版本、语言及 Schema 合同隔离，不能做商品默认值。
4. 离线聚合已审核样本，提出候选字段关系或值映射；先以频次和冲突统计建立可解释基线。数据足够后再评估监督式候选排序模型，输入可用来源标签、事实值特征、目标字段类型、品类/类型和作用域。模型输出只用于规则审核队列排序，不在在线匹配中补写未知字段。
5. 自动发现的候选规则经独立验证、人工审核、启用后才能被确定性引擎执行；上架人工确认的修正版本按上述例外立即启用。运行时仍要求规则适用、证据明确、Schema/字典合法；任一条件不满足就留空。

## 置信度设计

分别统计字段绑定、值映射和规则适用范围的可靠性，不用一个商品总分掩盖单字段风险。每项记录审核通过数、纠错数、独立商品数、供应商数、时间范围、冲突数、规则 revision 和合同版本。

同商品多次采集、同商品不同 SKU 的公共事实不重复算独立样本。没有人工审核的自动命中不进入正确率分母，避免用模型或规则自己的输出证明自己正确。优先补充不同供应商、不同类型、困难负例的复核样本。

建议同时报告 `verifiedAccuracy = 正确审核数 / 已审核数` 与不确定性区间、小样本标记及覆盖率。零样本不赋予默认高分。置信度用于候选审核排序和启用门禁，不能替代字典合法性校验，也不能授权未知字段自动填值。

用户已确认：每条规则/值映射在对应版本和范围内，至少 100 次有效人工校验、正确率 ≥98% 可设为 trusted。统计信任不替代适用性和目标合同检查，也不阻止已确认人工修正版立即启用。验证集按商品/供应商隔离，并保留时间后移样本，防止同源 SKU 泄漏导致虚高分。

## 生命周期与漂移

- draft：从已审核样本提出，尚不能全局生效。
- candidate：多样本验证中，仅影子评估，不写入商品目标值。
- trusted（旧规划称 stable）：达到至少 100 次有效人工校验且正确率 ≥98%，按明确范围标记统计可信。启用与可信分开记录，人工确认的修正版本可以先启用、再积累统计。
- revalidation_required：Schema、采集器、规范化或引擎版本变化，或纠错率超门槛，暂停受影响自动匹配，回到人工队列。
- disabled：被明确禁用；保留历史 revision，支持回滚。

从 TypeOverride 晋升 CategoryCommon 必须有跨类型证据，不能用单类型的高准确率代表整个品类。历史缺陷和负例必须纳入回归。撤销标签后应重算统计并复核受影响规则；版本回滚不得覆盖人工已确认的商品结果。

## 建议实施顺序与验收

P0：人工编辑、合法字典选择、保存与审核、待办队列、按 SKU 必填阻断。验收未知字段始终空白、人工来源可追溯、非法 ID 无法保存为通过状态。

P1：持久化审核事件、不可变规则 revision、双知识库隔离、启停与回滚；建立覆盖率、已审核精度、人工纠错率、待办数量和处理时间报表。统计必须支持按品类/类型/字段拆分。

P2：离线候选发现、独立验证集、影子运行、置信度校准与漂移监控；与纯规则基线比较人工工作量和错误率，收益不足时继续使用规则和人工。

P3：多设备/云同步按既有 Outbox、幂等与冲突设计推进。训练参数尚待真实审核数据支持，可信门槛已按用户要求定为至少 100 次有效校验且正确率 ≥98%，本次不部署模型、不自动晋升任何规则。

## 本次规则变更与验证

- 全部商品/SKU 的 fallback：两轮 Qwen 补齐 → 无模型调用，待人工空值。测试空目录、无 API Key、必填/选填空值、取消。
- 字典选择：AI 在候选中选择 → 仅确定性绑定加唯一精确字典命中；无结果、近似、多 ID 同文和接口失败留空。测试精确成功、查询去重、无结果、失败、近似与冲突。
- 不合法规则值：约束错误保留值 → 清空目标值并保留诊断。测试错误标量与其他合法属性共存。
- SKU 覆盖：过滤未解决行可能回填公共值 → 未解决 SKU 覆盖先抑制公共值，再过滤可用值。测试缺失 SKU 证据及草稿不回填。

公共模块内容、分类绑定目录、TypeOverride 优先级、SKU 身份生成、类型冲突前置阻断和分组政策未新增业务规则；学习生命周期与置信度均为规划，没有悄然启用。
