# AM 数据抓取模块逻辑

## 1. 模块边界

数据抓取模块只负责从 1688 获取可审计的源数据，不负责字段匹配、Ozon 属性转换或自动上架。

输入是一个搜索任务：

```text
关键词：手机壳
采购价格范围：可选
排序方式：默认销量优先，可选价格优先
详情抓取范围：搜索结果中的全部有效商品
```

输出是一个抓取任务结果：一份商品列表 JSON，以及列表中每个商品对应的一份详情事实。任何后续模块都只能使用这个结果，不应重新解析网页。

## 2. AM 文件职责

| 职责 | AM 文件 | 责任 |
| --- | --- | --- |
| 列表页采集 | `plugin/content/extractor.js` | 读取搜索结果卡片，提取标题、价格、图片和详情链接，按原始顺序输出列表 JSON |
| 详情页事实采集 | `plugin/content/detail-extractor.js`、`plugin/lib/detail-facts.js` | 在真实渲染的 1688 详情页中读取页面事实、图片、属性和 SKU |
| 任务编排与页面控制 | `plugin/background.js` | 打开/复用搜索页，应用筛选排序，滚动加载列表，逐条打开详情页并隔离单商品异常 |
| 扩展弹窗 | `plugin/popup.js`、`plugin/popup.html` | 显示任务进度、列表数量、成功/部分成功/失败数量和采集警告 |
| 桌面端请求入口 | `src/AutoMagic.Infrastructure/Bridge/DesktopBridgeService.cs`、`src/AutoMagic.Contracts/Protocol/BridgeProtocol.cs` | 接收桌面端采集任务并把最终结果返回桌面端 |
| 桌面端任务状态 | `src/AutoMagic.Desktop/ViewModels/MainViewModel.cs` | 发起搜索、展示列表和详情事实、保存当前批次状态 |
| 采集协议 | `src/AutoMagic.Contracts/Protocol/BridgeProtocol.cs` | 定义搜索任务、列表商品、详情事实和逐商品结果的 JSON 合同 |
| 采集测试 | `test/*.test.mjs`、`tests/AutoMagic.Contracts.Tests/*` | 验证列表提取、详情事实、SKU、协议和失败隔离 |

## 3. 端到端流程

### 3.1 创建任务

桌面端发送唯一 `requestId` 和关键词 `手机壳`。插件只访问 `*.1688.com`，复用当前用户的 Chrome 登录态，不处理登录、验证码或访问限制。

任务状态依次为：

```text
created → searching → list_ready → collecting_details → completed
```

搜索或列表页本身失败时，任务进入 `failed`，因为没有可供遍历的详情链接。

### 3.2 搜索和列表 JSON

1. 复用当前窗口已有的 1688 搜索结果页；没有则打开搜索页。
2. 读取搜索框，只有关键词不一致时才输入并触发 Enter。
3. 应用采购价格筛选并以 URL 参数确认筛选生效。
4. 应用排序。
5. 从页面顶部开始按固定间隔滚动，直到列表加载完成。
6. 读取搜索结果中的全部商品卡片，按页面原始顺序写入列表 JSON。
7. 列表 JSON 不做校验、过滤或去重；页面返回什么，就按原样保存什么。

每条列表记录至少包含：

```json
{
  "list_index": 1,
  "title": "商品标题",
  "price_text": "¥1.20-2.80",
  "main_image_url": "https://...",
  "detail_url": "https://detail.1688.com/offer/...html"
}
```

列表 JSON 必须在详情抓取开始前固定下来，后续详情结果通过列表位置和详情链接与列表记录关联。列表记录不额外添加来源平台或链接校验结果。

## 4. 全量详情抓取

列表中的每一条详情链接都要尝试访问，按列表顺序逐条处理，不做去重。单个商品是一个独立的处理单元：

测试阶段临时只处理列表前 10 条详情，列表 JSON 仍完整保存；该限制不属于正式业务逻辑，正式采集时应移除。

```text
打开详情页
→ 等待页面完成和关键区域渲染
→ 采集详情事实
→ 关闭临时标签页
→ 写入该商品结果
→ 继续下一个商品
```

页面打不开、超时、被重定向、脚本异常或字段缺失，都只能影响当前商品。当前商品保留列表记录和已经取得的内容，并设置状态后继续。建议状态为：

```text
success  页面可访问，事实采集完成
partial  页面可访问，但有字段、图片或 SKU 缺失
failed   页面无法访问或没有取得可用详情事实
```

没有可访问详情链接的列表记录也要保留在最终结果中，并标记该条详情结果失败或缺失原因。最终任务结果必须同时提供列表原文、总数、成功数、部分成功数、失败数，以及每个商品的错误信息和警告。

## 5. 详情事实模型

“详情事实”是某个商品页面实际读取到的源事实集合，不是字段匹配结果。每条事实保留原始文本和采集来源：

```json
{
  "product_index": 1,
  "detail_url": "https://detail.1688.com/offer/...html",
  "captured_at": "2026-09-14T00:00:00Z",
  "status": "success",
  "facts": [
    {
      "fact_id": "fact-001",
      "name": "材质",
      "value": "TPU",
      "scope": "product",
      "source": "dom_semantic",
      "source_text": "材质：TPU"
    },
    {
      "fact_id": "fact-002",
      "name": "颜色",
      "value": "黑色",
      "scope": "sku",
      "sku_id": "1234567890",
      "source": "structured_json",
      "source_text": "黑色"
    }
  ],
  "images": [],
  "skus": [],
  "warnings": [],
  "errors": []
}
```

事实来源按可信度记录为 `structured_json`、`script_init_data`、`dom_semantic`、`candidate_selector` 或 `unknown`。页面没有提供某字段时使用缺失诊断，不用模型猜测或用相邻字段代替。

商品级事实和 SKU 级事实必须区分；同一字段的多个 SKU 值不能压缩成一个商品级值。

## 6. SKU 采集策略

SKU 采集按以下优先级取得证据：

1. 页面初始化脚本或结构化商品数据中的真实 SKU ID、规格组合、价格、库存和图片。
2. 页面可见的 SKU 组合控件和规格属性，用于补充结构化数据缺失的组合信息。
3. 单规格商品没有组合表时，生成明确标记为 `single_specification` 的单规格记录；这不是伪造 1688 SKU ID。
4. 只有名称或页面文字、没有规格组合证据的内容，不得当作 SKU。

每个 SKU 至少保留：

```json
{
  "sku_id": "1688真实ID或null",
  "sku_identity_type": "1688_sku",
  "sku_name": "黑色 / iPhone 15",
  "option_values": [
    { "name": "颜色", "value": "黑色", "source_text": "黑色" }
  ],
  "price": null,
  "stock": null,
  "availability": "unknown",
  "image_url": null,
  "sku_image_missing": true,
  "selection_order": 1,
  "source_data": {}
}
```

SKU 图片缺失不阻塞商品采集；必须保留 `sku_image_missing=true`。SKU 价格缺失时保留产品价格区间作为独立的产品级事实，不能无证据地伪造 SKU 专属价格。

## 7. 图片采集

图片分为主图、详情图和 SKU/规格图。采集器应先读取真实 URL，再由下载层处理本地保存、去重和失败记录。每张图片保留原始 URL、来源类别、顺序、下载状态和错误信息。

图片懒加载处理顺序为：读取 `currentSrc/src`，再读取 `data-src`、`data-original`、`srcset` 和背景图；必要时滚动图片区域触发加载。无法读取的图片只产生告警，不影响其他字段和其他商品。

## 8. 原始快照与诊断

每个商品都应保留必要的原始快照或快照引用，包括页面最终 URL、页面标题、结构化脚本候选、关键 DOM 文本、SKU 原始数据和采集器版本。快照用于复核采集器，不交给字段匹配模块直接当作已验证字段。

诊断至少包括：

- 列表总卡片数和详情处理结果数量；
- 详情页面最终 URL 和页面加载耗时；
- 每个字段使用的采集策略、候选数、是否命中和失败原因；
- SKU 总数、真实 ID 数、缺图数、缺价数；
- 主图、详情图和 SKU 图的成功/失败数量；
- 当前商品错误、警告和任务整体错误。

## 9. AM 第一版验收标准

使用关键词“手机壳”时：

1. 能在 1688 搜索并返回商品列表 JSON。
2. 列表中的每条详情链接都被按原始顺序尝试访问，不做去重。
3. 详情结果数量与列表记录数量一一对应，顺序可追溯。
4. 每个商品都有独立的详情事实对象，即使为空或部分成功。
5. 一个详情页失败不会阻塞后续商品。
6. 商品级事实、SKU 级事实、图片和原始证据不会混淆。
7. SKU、图片或字段缺失时保留缺失状态和诊断，不进行猜测。
8. 任务完成后能清楚报告成功、部分成功和失败数量。

## 10. 本地固定输入

采集任务完成后，AM 必须把以下内容完整保存到本地：

1. 原始商品列表 JSON，保持页面返回顺序和内容，不做去重或过滤；
2. 每个列表商品对应的详情事实对象；
3. 每个详情对象的抓取状态、警告、错误和原始快照引用；
4. 任务元数据和采集时间。

这份本地结果是字段匹配模块的固定输入。字段匹配只读取这份快照，不重新访问 1688，也不依赖当前浏览器页面状态。

第一版实现顺序建议是：先完成列表原样保存、全量详情遍历、逐商品结果合同和本地固定快照，再补齐结构化 SKU、多来源属性、图片懒加载和原始快照；字段匹配模块只消费最终本地快照，不参与网页采集控制。
