# AM 上架流程设计

更新：2026-10-15。本文记录已与用户确认的 1688 → Ozon 上架方案。除"当前状态"一节外均为待实现设计；标注"未核实"的内容需在首次真实调用时确认。

## 当前状态

- 已实现：插件采集、原始事实与 SKU 保存、类目与类型选择、Schema 查看与缓存（含 is_required / is_aspect；缺 is_aspect 的旧缓存会被拒绝，需手动刷新一次）、清洗前必填属性覆盖校验（8292 由系统生成，豁免）、rules/clean 清洗（200000933 / 93182 七项属性）。
- 未实现：match 字典匹配（规则 JSON 保留）、人工修订、offer_id、AI 文本与图片、请求组装、提交、状态查询、库存推送。

## 流程

```text
A 创建采集任务
B 插件采集并返回
C 保存原始事实与 SKU
D 确认类目与类型
E 加载 Schema 与字典（含 is_required / is_aspect）
   ◇ 类型方案覆盖全部必填属性？ ──否──▶ 配置错误，修正规则
F 规则清洗
G 字典匹配 + 重放商品修订            ◀──────────────┐
   ◇ 有阻断项？ ──有──▶ I 人工补全 ──▶ J 保存修订 ──┘
T AI 生成俄文文本、处理图片并存 CDN
   ◇ 人工审核模式？ ──是──▶ 人工确认草稿（发现问题回到 I）
K 组装提交 JSON（offer_id、8292 分组值）
   ◇ 冻结前校验通过？ ──否──▶ 回到 I
L 冻结发布快照
M 提交 Ozon
N 查询导入与审核结果，写入 offer_id 对照表，推送库存
```

## 清洗与匹配

- 清洗在确认类型之后执行；E 之后先比对 Schema 必填属性，缺规则即为配置错误。8292 由系统生成，不需要清洗规则。
- 兜底值（fallbackValue）只在源字段缺失时使用。源字段有值但条件未命中时，原样输出源值交给 match；match 查不到则留空交人工。
- 默认值只放在 clean，match 只负责中文值到 targetValue / valueId 的映射，不设 defaultValue。
- 连衣裙（93182）性别默认"女性"，仅放在该类型专用模块，仅源字段缺失时使用。Schema 说明童装用"女孩/男孩"，同样在 93182 下；童裙且源数据无性别的情况为已接受的残余风险。
- 品牌缺失时填"无品牌"，这是 Ozon 属性 31 说明中的要求。
- 尺码使用人工批准的固定换算表，按适用人群拆分（先做女装），由类目显式引用，不放全局通用表。表中没有的值留空。换算数值需用户逐条核定。
- 性别、颜色、尺码、品牌等字典标记为 category_dependent，valueId 必须按类目和类型从真实字典核对。现有 match 字典中的 valueId 未核实。

## 商品级与 SKU 级

- 不在规则中配置层级，按来源决定：来自 1688 规格轴的值为 SKU 级，其余为商品级。
- 商品级属性人工确认一次，提交时复制到每个 SKU；Ozon 只接收逐 SKU 的独立条目。
- 变体属性只认 Schema 的 is_aspect，不做类型方案兜底。93182 的变体属性：4295 俄罗斯尺码、10096 商品颜色、9533 制造商尺码（自由文本，写源尺码）、10097 颜色名称（自由文本）。
- 冻结前校验同一卡片下的 SKU 至少有一个变体属性值不同。校验放在 AI 翻译之后，避免"本白""米白"译成同一个词后无法区分。

## 人工修订与存储

- 修订默认只对当前商品生效，按（商品、属性、源值）保存，重新清洗时重放。
- 沉淀为规则必须由用户点击"加入规则"，写入 rules/match 的 JSON，git 历史作为规则审计。系统不自动升级重复修订。
- 修订、规则沉淀来源、offer_id 对照表放在用户数据目录下的新 SQLite 库，不放在 rules/。

## 人工填写项

价格、包装尺寸、重量由人工填写：商品级填一次，个别 SKU 可覆盖。定价公式推迟，以后替换价格来源，不改流程结构。

## AI 使用范围

- AI 只处理自由文本和图片：俄文标题、描述、10097 颜色名称；图片处理后存 CDN（公开 HTTPS）。
- AI 输入只用已确认的属性和源标题；AI 产出不参与字典匹配或属性推断。
- 图片处理不得改变商品颜色或款式，并保留图片与颜色变体的对应关系。

## 运行模式

- 自动模式：只跳过确认类步骤（AI 文本、已匹配值）。
- 阻断项（未匹配值、缺少价格或尺寸重量、变体不可区分）在两种模式下都拦下该商品，同批其他商品照常提交。
- 人工审核模式：所有商品在 K 之前停下等人工确认。
- 两种模式共用一条流程和一套校验，只差一个开关。
## offer_id 与卡片合并

- offer_id = 36 进制源商品 ID + "-" + 规格值组合的 4 位 36 进制短哈希，例如源商品 925890695648 的前缀为 `BTCJEX28`，offer_id 形如 `BTCJEX28-7K2Q`。不含平台前缀、中文或翻译。
- 同一商品内撞号时加长一位。首次生成后固定保存，供应商改规格名称或顺序也不重新生成，保证重复提交为更新。
- 8292"合并至一张卡片"值为 `1688-{源商品 offerId}`，同一条采集商品的全部 SKU 共用。这是项目内部约定，Ozon 只要求值不要过于简单、不含类型和品牌。
- 对照查询页：按 offer_id 或 1688 商品 ID 查询，显示源商品、规格值和最近一次提交状态。货源追溯和采购不属于 AM 职责。
- 未核实：Ozon 对 offer_id 的长度与字符限制。

## 提交与状态

- `/v3/product/import` 单次最多 100 个商品，可新建或更新，同时设置基础价格和图片；新商品审核通常约 3 天（来源：Ozon 官方 API 文档搜索摘要）。
- 按商品分批，一个商品的所有 SKU 不拆到不同批次。
- 状态分两段：导入结果、审核结果，均写入 offer_id 对照表。
- Ozon 返回的属性错误按 offer_id 和属性 ID 回挂到人工补全。
- 部分 SKU 失败时保留成功的，只重新提交失败的；8292 相同，会合并回同一卡片。
- 未核实：task_id 与 `/v1/product/import/info` 的结果结构、审核状态查询接口。

## 库存

- 上架后推送初始库存，默认每个 SKU 99，界面可修改：商品级设一次，SKU 可覆盖，可一键清零。1688 规格组合不证明有货，缺货 SKU 应改为 0。
- 履约方式由店铺仓库查询决定，不在录入密钥时手动选择。没有 FBS/rFBS 仓库时跳过库存推送并提示。
- 目标仓库由用户在店铺设置中指定默认仓库；只有一个仓库时自动选中；可按商品修改。
- 未核实：`/v1/warehouse/list` 与库存推送接口的字段。

## 冻结快照

L 记录 Schema 与字典的拉取时间、规则文件版本、商品修订版本、AI 文本和 CDN 图片地址，保证能复现每次提交的内容。

## 推进顺序

1. Schema 解析保存 is_aspect，加必填属性完整性校验。
2. 重建 match，接上 clean 输出。
3. SQLite：修订层与 offer_id 对照表。
4. 按商品级 / SKU 级组织的审核界面。
5. 组装请求、冻结快照、提交、轮询状态。
6. 库存推送，接入 AI 文本与图片。

前 5 步可先用人工填写的俄文标题跑通，不依赖 AI 服务。
