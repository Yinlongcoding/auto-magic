# 完整处理流程

## 核心原则

**先验证，后调用AI** - 只有通过规则验证的商品才消耗AI资源

---

## 详细流程

### 阶段1：任务创建和抓取

```
[人工] 选择Ozon类目（如：女装 > 连衣裙 93182）
         ↓
[系统] 加载该类型的Schema（必填项、变体属性、字典）
         ↓
[系统] 根据类型ID查询规则类目（93182 → women-apparel）
         ↓
[系统] 加载规则文件
         ├─ categories/women-apparel/brand.json
         ├─ categories/women-apparel/color.json
         ├─ categories/women-apparel/size.json
         └─ categories/women-apparel/gender.json
         ↓
[人工] 输入1688关键词（如：连衣裙 女装）
         ↓
[人工] 设置定价规则（如：成本 × 6.5 × 1.8）
         ↓
[系统] 调用1688采集插件，抓取前50个商品
         ↓
[系统] 保存原始数据到数据库
```

---

### 阶段2：规则处理（批量自动）

对每个抓取的商品：

```
[系统] 规则引擎处理
         ├─ 品牌映射（1688品牌 → Ozon valueId）
         ├─ 颜色映射（1688颜色 → Ozon valueId）
         ├─ 尺码换算（中国码 → 俄罗斯码 valueId）
         ├─ 性别（默认"女性"）
         └─ 价格计算（应用定价公式）
         ↓
       判断阻断？
         ├─ 必填属性缺失？
         ├─ 变体属性无法映射？
         ├─ 价格为0或异常？
         └─ SKU变体无法区分？
         ↓
       ├─ 有阻断 → 标记状态：待人工处理
       └─ 无阻断 → 标记状态：待AI处理
```

**输出**：
- 50个商品分为两组
  - 待人工处理：10个（有阻断项）
  - 待AI处理：40个（规则全部通过）

---

### 阶段3：人工处理阻断项

```
[系统] 展示"待人工处理"列表（10个商品）
         ↓
[人工] 逐个查看阻断原因
         ├─ 品牌无法映射 → 手动选择或补充映射规则
         ├─ 颜色"香芋紫"无法映射 → 手动选择"紫色"
         ├─ 尺码"均码"无法换算 → 手动选择俄罗斯码
         └─ 价格异常 → 手动调整
         ↓
[人工] 确认修改
         ↓
[系统] 重新运行规则引擎（使用人工补充的值）
         ↓
       再次判断阻断？
         ├─ 仍有阻断 → 继续人工处理或放弃该商品
         └─ 无阻断 → 移入"待AI处理"队列
```

**输出**：
- 待AI处理：48个（40个自动通过 + 8个人工修复）
- 放弃：2个（人工决定不上架）

---

### 阶段4：AI处理（批量自动）

**仅处理"待AI处理"队列中的商品**

```
对每个商品：

[AI] 翻译俄文标题
    输入：1688标题 + 已确认的属性（颜色、尺码、品牌等）
    输出：俄文标题（符合Ozon SEO规范）
         ↓
[AI] 翻译俄文描述
    输入：1688详情 + 规格信息
    输出：俄文描述（补充卖点）
         ↓
[已移除] AI 推断可选属性：与 AGENTS.md 的 AI 范围冲突，可选属性第一阶段留空不提交（见 12 号文档）
         ↓
[系统] 下载 1688 图片，原样上传到 OSS（第一阶段不做 AI 图片处理，见 12 号文档）
    输入：1688 原图
    输出：稳定的 HTTPS 链接
         ↓
[系统] 保存AI生成的数据到数据库
         ↓
标记状态：待提交
```

**输出**：
- 待提交：48个商品（完整的Ozon商品数据）

---

### 阶段5：人工审核（可选）

如果开启了"人工审核模式"：

```
[系统] 展示"待提交"列表
         ↓
[人工] 快速浏览AI生成的内容
         ├─ 俄文标题是否合理
         ├─ 图片处理是否正确
         └─ 可选属性是否合理
         ↓
[人工] 确认或修改
         ↓
批量提交
```

如果是"自动模式"，跳过此步骤，直接提交。

---

### 阶段6：组装和提交

```
[系统] 组装Ozon API请求
         ├─ 生成offer_id（36进制ID + 规格哈希）
         ├─ 生成8292合并卡片值（商品ID的36进制编码）
         ├─ 组装每个SKU的完整属性JSON
         └─ 包含OSS图片链接
         ↓
[系统] 冻结发布快照（记录规则版本、AI生成时间等）
         ↓
[系统] 批量调用Ozon API（/v3/product/import）
         ├─ 每批最多100个商品
         ├─ 同一商品的所有SKU不拆分
         └─ 记录task_id
         ↓
[系统] 轮询导入结果
         ↓
[系统] 保存offer_id对照表
         ↓
[系统] 推送初始库存（默认每SKU 99）
```

```

                      └─→ [被拒绝] 需要修改
```

## AI成本控制

### 只为通过验证的商品调用AI

**场景1**：抓取50个商品
- 40个自动通过 → 调用AI（40次）
- 10个有阻断
  - 8个人工修复后通过 → 调用AI（8次）
  - 2个放弃 → 不调用AI（节省成本）

**AI调用次数**：48次（而不是50次）

**成本节省**：避免为失败商品浪费AI资源

---

### 批量调用优化

**进一步优化**：
- AI翻译和图片处理可以批量并发
- 例如：48个商品，可以并发调用12个AI任务（每次4个商品）
- 减少总处理时间

## 配置选项

### 1. 人工审核模式（用户配置）

**配置项**：`settings.requireManualReview`
- `true`：AI处理完后，需要人工审核才能提交
- `false`：AI处理完后，自动提交

**用户界面**：
```
□ 需要人工审核AI生成的内容
  （标题、描述、图片处理结果）
```

---

### 2. AI失败处理策略

**自动重试机制**：
- 最多重试3次
- 重试间隔：2秒、5秒、10秒（指数退避）

**3次重试后仍失败**（按字段区分，详见 12-ai-integration.md）：
- 俄文标题、10097 颜色名称 → **阻断**，退回待人工处理，不受审核开关影响
- 俄文描述 → 开启人工审核则阻断；关闭则留空，继续提交

**逻辑**：
- 标题和颜色名称是必须有的字段，留空会导致提交失败或 SKU 无法区分
- 描述缺失不影响提交，自动模式下避免单个商品阻塞整批

---

### 3. 批量大小

**默认值**：每次抓取50个1688商品

**用户界面**：
```
抓取数量：[50] 个商品

```

## 重复商品处理策略

### 问题场景

用户第一次搜索"连衣裙"抓取了50个商品。
第二次再搜索"连衣裙"，可能有30个商品和第一次重复。

### 判断重复的依据

**1688商品唯一标识**：`offerId`（1688商品ID）

**何时算重复**：
- 同一个1688 offerId 已经在系统中存在
- 无论该商品处于什么状态（待处理、已提交、已上架等）

### 处理策略（待选择）

#### 方案A：跳过重复商品
```
抓取50个商品
  ├─ 30个已存在 → 跳过
  └─ 20个新商品 → 保存

提示用户："已跳过30个重复商品，新增20个商品"
```

**优点**：简单，避免重复处理
**缺点**：1688商品可能已更新（价格、库存、图片），跳过会丢失更新

---

#### 方案B：检测但让用户选择
```
抓取50个商品
  ├─ 30个已存在 → 标记为"重复"
  └─ 20个新商品 → 标记为"新增"

弹窗询问：
"发现30个重复商品，如何处理？"
  [跳过重复] [更新数据] [查看详情]
```

**优点**：灵活，用户可以选择是否更新
**缺点**：每次都要人工决策，降低效率

---

#### 方案C：自动更新已存在的商品
```
抓取50个商品
  ├─ 30个已存在
  │    ├─ 状态=已上架 → 跳过（不覆盖已上架的）
  │    ├─ 状态=待处理 → 更新原始数据，保留人工修改
  │    └─ 状态=已放弃 → 重新激活，更新数据
  │
  └─ 20个新商品 → 保存

提示用户："更新了15个商品，跳过15个已上架商品，新增20个商品"
```

**优点**：智能处理不同状态，避免覆盖已完成的工作
**缺点**：逻辑复杂

---

#### 方案D：基于状态的处理矩阵

| 已存在商品的状态 | 处理方式 | 说明 |
|---|---|---|
| 已上架 | **跳过** | 不覆盖已成功上架的商品 |
| 审核中 | **跳过** | 已提交给Ozon，不干扰 |
| 待提交 | **询问** | "要覆盖这个已处理好的商品吗？" |
| 待AI处理 | **更新** | 更新原始数据，重新处理 |
| 待人工处理 | **更新** | 更新原始数据，保留人工已修改的值 |
| 已放弃 | **询问** | "要重新启用这个商品吗？" |

**优点**：最精细的控制，符合各种场景
**缺点**：逻辑最复杂，需要仔细设计

---

### 我的推荐：方案C的简化版

```python
# 伪代码
for product in scraped_products:
    existing = database.find_by_1688_id(product.offer_id)
    
    if existing is None:
        # 新商品，直接保存
        database.insert(product)
        new_count += 1
    
    elif existing.status in ["已上架", "审核中"]:
        # 已经提交给Ozon的，不动
        skipped_count += 1
    
    elif existing.status in ["待处理", "待人工处理", "待AI处理"]:
        # 还在处理中的，更新原始数据，保留人工修改
        database.update_source_data(product, preserve_manual_edits=True)
        updated_count += 1
    
    elif existing.status == "已放弃":
        # 之前放弃的，重新激活
        database.reactivate(product)
        reactivated_count += 1

# 提示用户
print(f"新增{new_count}个，更新{updated_count}个，重新激活{reactivated_count}个，跳过{skipped_count}个")
```

**核心逻辑**：
1. 已经提交给Ozon的商品（已上架、审核中）→ 不动
2. 还在本地处理的商品 → 更新原始数据
3. 已放弃的商品 → 重新激活

**为什么要"保留人工修改"**：
- 用户可能已经手动补充了颜色、尺码等属性
- 更新原始数据（1688标题、价格、图片URL）
- 但不覆盖用户手动填写的Ozon属性值
