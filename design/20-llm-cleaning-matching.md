# LLM 清洗与匹配 + 知识库沉淀方案

状态：2026-10-29 讨论确认（第 17 条待定）。本方案取代/修订 12 号、18 号的相关边界，见文末"对已有文档的影响"。

## 一、背景与动机

- 原方案：手写规则（`rules/mappings/*.jsonl`）+ 本地规则引擎做清洗和匹配。问题：规则维护成本高、周期长。
- 现状：人工确认不明确的值只写进批次级 `manual_edits`（"应用到本批次"），"记录到规则"（写回 rules/ 文件）这一步**未实现**，规则只能手改文件，闭环是断的。
- 决策：改用 **LLM 做"清洗 + 语义初匹配"**，本地程序做 valueId 绑定；并引入**知识库沉淀**机制替代手写规则维护。

## 二、核心原则

1. **LLM 永不产出 valueId**，只产出候选中的规范值/规范名。
2. valueId 由本地程序绑定 + 校验。
3. 清洗匹配按**整商品（整组）**处理，保证变体属性清洗后两两不同、不塌缩。

## 三、分工边界

| 环节 | 谁做 | 说明 |
|---|---|---|
| 去营销后缀 | 本地（正则） | 如 -现货、-新款 |
| 尺码字母→俄码 | 本地（查表） | 已有表，逐条核定 |
| 源值精确命中字典唯一名 | 本地（字典同名层） | 免费确定性快路径 |
| 颜色归一 / 类型推断 / 其他脏值归一 | LLM | 语义清洗 |
| valueId 绑定 + 校验 | 本地 | valueId∈候选、axis 去重、置信度门槛 |

现有 `SourceNormalizer`（去括号/拆段/前缀匹配）与"字典同名"层**保留**，作为免费确定性快路径；LLM 只兜底剩下的脏值。

## 四、LLM 清洗模块机制

### 4.1 候选值
- 候选 = Ozon 字典值，程序已下载（TypeSchemaCache），**自动筛，无需人工提供**。
- 筛法：**子串匹配**（已确认），源值在字典里捞相关候选，约 10~30 条，控制 Prompt 规模。

### 4.2 调用单位
- 按**整商品一次调用**（不是逐值），保证"变体清洗后两两不同"。

### 4.3 输入契约
```json
{
  "product": {
    "title": "夏季小个子仙气飘飘吊带晚礼服裙子",
    "attributes": { "sleeve": "无袖", "length": "长裙" },
    "axes": [
      { "name": "颜色", "values": ["白色","月白色","黑色","芒果黄","落日红"] }
    ]
  },
  "targets": [
    {
      "attribute": "color",
      "candidates": [
        { "valueId": 61571, "value": "白色" },
        { "valueId": 61562, "value": "灰色" },
        { "valueId": 61588, "value": "黑色" },
        { "valueId": 61596, "value": "黄色" },
        { "valueId": 61590, "value": "红色" }
      ]
    }
  ]
}
```

### 4.4 输出契约
```json
{
  "axes": [
    {
      "name": "颜色",
      "mapping": [
        { "source": "白色",   "valueId": 61571, "value": "白色", "confidence": "high" },
        { "source": "月白色", "valueId": null,  "value": null,   "confidence": "low", "reason": "候选无精确对应" },
        { "source": "芒果黄", "valueId": 61596, "value": "黄色", "confidence": "medium" }
      ]
    }
  ]
}
```
- `valueId` 只能从输入 `candidates` 里取（本地校验，防幻觉）。
- 允许 `low + null` → 进人工，不硬猜。

### 4.5 置信度
- high / medium / low 三档，**纯 LLM 自报**（已确认，暂不加本地二次判定）。
- high、medium 直接绑定；low 进人工。
- 持续观察数据波动，必要时再加一层兜底。

### 4.6 可靠性四前提
1. 约束词表（候选）
2. 整组喂（不是逐值）
3. 温度 0 + 结果缓存
4. 置信度门槛 + 允许"不确定"

### 4.7 token 成本结论
- DeepSeek 下成本不是瓶颈（全量 651 条也才约 ¥2/天）；限制候选是为**准确度和速度**，不是成本。

## 六、重名消歧（待定）

实测：颜色字典 651 条有 **52 个中文重名**（"酒红色"有两条 61590 / 972075870），ZH_HANS 响应的 `info` 字段全空（俄文不在其中）。

**待定（第 17 条）**：是否保留"拉 Ozon 权威俄文"做重名兜底。
- 倾向 A：清洗归一基础色（唯一名），重名色号不成为输出，无需俄文兜底；必须保留色号的重名场景走 low 置信度 → 人工。
- 备选 B：拉权威俄文塞进候选，让 LLM 在重名条目间选。

## 七、知识库沉淀机制

### 7.1 沉淀来源
- LLM 结果、人工确认 → **自动沉淀**（append-only），替代手工"写入规则"。

### 7.2 查找顺序
```
人工修订(batch) > 知识库(沉淀) > 字典同名 > LLM > 失败进人工
```

### 7.3 质量门槛
- high 自动沉淀。
- medium 先人工确认、确认后沉淀。
- 留"查看/撤销/覆盖"入口（防错误固化，让知识库"越用越准"而非"越用越多"）。

### 7.4 种子
- `rules/` 现有 36 条颜色 + 12 条尺码 → 当知识库**种子**（origin=seed）灌入。

## 八、三阶段路线与关键约束

- **阶段一**：应用 + 本地规则库。
- **阶段二**：日积月累完善（配纠错入口）。
- **阶段三**：SQLite 迁服务端 API（触发条件：多机器 / 共享 / 多人用）。

关键约束（阶段一就要立，决定阶段三是"一天"还是"一个月"）：
- `IMatchingService` 接口（本地/远程两实现）。
- `match_rule` 纯规则表：scope / attribute_id / source / value_id / label / confidence / origin / updated_at，**不掺本地路径、批次 ID、UI 状态**。

## 九、本地数据清单

- Ozon 权威字典（schema + 字典值，已有 TypeSchemaCache）
- 候选检索（子串，不建索引）
- 确定性小表（尺码换算、品牌/性别/类型固定值）
- LLM 结果缓存（全局、跨批次）
- 匹配追溯（层：manual > llm > dictionary > table）
- 采集源数据 + manual_edits + 最终 attributes（已有）
