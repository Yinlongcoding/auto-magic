# 规则引擎

## 已确认：分层覆盖，并记录每个属性命中的层（方案 C）

- 规则按全局、类目、类型三层合并，后者覆盖前者（见 05 号文档）。
- 每次处理时，为每个属性记录最终命中的层（全局、类目、类型、人工修订）和规则文件名，写入 processed_data / product_skus.attributes 的对应条目，供追溯。
- 优先级沿用此前讨论：人工修订 > 类型规则 > 类目条件规则 > 类目标准规则 > 留空（必填则阻断）。

## 规则来源（已确认：先手写高频，其余走沉淀）

- 高频、有把握的规则先手写：基础颜色、标准尺码换算（尺码换算涉及俄码，由开发者逐条核定）。
- 长尾值走沉淀：遇到未匹配值，在表单里选定结果后写入规则文件。
- 开发阶段用大量真实商品和数据在本地版本测试，逐步完善初期规则。规则编辑不靠手改 JSON。

## 规则编辑表单（已确认：仅开发版本）

规则编辑权限仅开发者拥有，正式发布的桌面应用不含此表单。

表单行为：

- 自动带出上下文：属性、源值、当前类型、命中的层。
- 目标值从该类型已缓存的 Ozon 字典中选择，不允许手填 valueId。
- 写入层：默认写到当前类型所属的类目层，并提供"仅此类型"开关，打开则写到类型层（已确认，方案 C）。
- 写入前检查冲突：同一源值在该层已映射到别的值时，提示并让用户选择覆盖或取消。
- 写入前显示影响范围，如库内另有 N 个商品含该源值。
- 写入规则文件本身，改动进 git 留历史。写完自动重跑受影响的商品。

以上除"写入层"外，都是我提出的建议，用户确认了需求但未逐条确认细节。

## 对发布形态的影响

- 发布版没有规则编辑器，规则文件随应用发布，用户只读。用户遇到未匹配值只能通过 manual_edits 处理当前商品，不会改动规则。
- 因此 manual_edits 里"加入规则"的字段（promoted_to_rule）在发布版没有用途，只在开发版使用。
- 规则文件放哪里：开发版放仓库目录，发布版随应用打包。具体位置待定。
- 规则更新靠发新版本。使用者之间的规则不会自动共享，这是已知限制。

## 规则变更审计（用户提出，仅开发版本；细节为我的建议，待确认）

目的：让开发者改规则时更谨慎，随时能回答"我改了什么、影响了多少"。

写入前（确认对话框）：
- 改动内容：规则文件、层、属性、源值，旧目标值 → 新目标值（新增、修改、删除三种）。
- 影响范围：库内含该源值的商品数和 SKU 数；若写在类目层，列出会受影响的类型数。
- 已提交的商品（审核中、已上架）数量单独标出，并注明规则变更不会回溯修改它们。
- 冲突提示：该层已有不同映射时显示旧值，要求明确选择覆盖。
- 校验：目标 valueId 必须在该类型缓存的字典里。

写入后（审计记录）：
- 时间、规则文件、层、属性、源值、旧值、新值、原因备注、影响范围快照。
- 重跑结果：受影响商品里有多少从阻断变为通过、多少匹配值发生改变。匹配值被改变的商品列出来供复查。
- 规则文件改动本身进 git，diff 即变更内容的审计。

沿用旧仓库 AGENTS.md 的要求：每次规则变更需单独汇报，不隐藏在一般代码改动里。重做后是否沿用，待定。

## 规则文件格式（已确认方向：按行存储，层级作为一列；方案 C）

- 规则存成行：`(scope, 属性ID, 源值) → valueId`。scope 取 global、category:xxx、type:nnnn。源值缺失时的兜底是源值为 `<缺失>` 的一行，不再设 fallback 字段，也不设 defaultValue。
- 属性只需一个很小的声明文件：每个属性从哪些源字段取值。它很少改，表单不碰它。
- 查找顺序：类型层、类目层、全局层，命中即停，并记录命中的 scope（即追溯信息）。
- 表单只追加行并固定排序，git diff 基本只有新增行。
- 尺码换算与普通映射合并为同一种查表，不再单独设换算表阶段。
- 通用规整放代码里，不进规则表：去掉"码"、统一大小写和全半角。这是我的建议，没有用真实数据验证；纯查表对脏数据的覆盖能力要靠开发阶段的大量测试检验。
- 同一个字典的 valueId 在不同类型下是否一致（旧文档称 category_dependent）：2026-10-23 实测（类目 200000933 服装，类型 93211 无袖连衣裙、93216 运动衫、93232 卫衣），颜色字典（10096，651 条）三个类型下 id 和名称完全相同；俄罗斯尺码字典（4295）随类型不同，93216 比 93211 多 5 个值。结论：字典按（类目、类型、属性）分别缓存，规则写入时按目标类型的字典校验 valueId。

## AM 实现（2026-10-23，用户确认）

按无袖连衣裙 93211 的真实数据（25 个商品、576 个 SKU）实现，对上面的设计有以下补充和偏离：

- 文件布局：`rules/attributes.json` 是属性声明；`rules/mappings/{属性ID}.jsonl` 是规则行，一行一条 `{scope, attribute, source, valueId, label, note}`，按（层、源值）排序。每个属性一个文件，git diff 只落在改动的属性上。同一层同一源值重复即加载失败。
- 属性声明的 sources 为空表示不看源数据，永远按 `<缺失>` 查规则。品牌（全局层 Нет бренда）、性别、类型（类型层写死）都用这种方式。
- 查找顺序增加两层：人工修订最前；规则三层之后加"字典同名"——源值规整后与字典里唯一的中文名完全相同就直接用，不写规则。中文名重复的不走这层，必须写规则。
- 源值分三档剥离：原值；去括号、前导编号、"有现货"、尺码后的"码"；按"-""/""、"等拆段及开头的尺码字母。前一档在所有层都没命中才试下一档。拆出的几段指向不同值算未匹配；拆出的纯数字不参与（"M 80-110斤"的 80 是体重）。
- 前缀匹配：属性声明 `prefixMatch: true` 时，最后取能作为源值开头的最长已知值（"杏色大花"→杏色）。是模糊匹配，目前只给颜色打开，开发版属性报告里单列供复查。
- 女装尺码换算写在类型层，不写类目层：Ozon 类目 200000933"服装"同时包含男装、婴儿用品，太宽。
- 人工修订按（批次、属性、源值）存在批次上，不按商品各存一份；同批次后来补抓的商品自动套用。匹配结果不落库，每次按当前规则重算。
- 未决：发布版规则目录的位置。开发版从程序目录往上找仓库里的 `rules/`。

## 服务器部署（已决定：初版不考虑）

初版规则引擎只在客户端本地运行。规则放服务器、提供解析 API 的想法记为后话，不做设计。该方案的数据模型（按行存储）不阻碍以后迁移，这点已讨论过，不再展开。

## 发布版的人工修订复用范围（已确认：同一任务内复用）

- 用户在一个任务里为某个源值（如"香芋紫"）选定结果后，同一任务内其他含该源值的商品自动应用。
- 不写规则文件，不跨任务生效，不影响别的任务。
- 实现方式（建议，未讨论）：保存时给同一任务内含该源值的每个商品各写一条 manual_edits，仍按（商品、属性、源值）存储，不新增表。代价是同一任务后续新抓取的商品不会自动带上，需在抓取后重放一次。
- 不做全局复用，原因是发布版没有界面查看或撤销它，一次误选会悄悄影响以后所有任务。

## 与旧仓库约定的冲突（需知悉）

旧仓库 AGENTS.md 写明"只解析显式引用，不要恢复隐式的 common、category、type 继承或回退搜索"。本设计的分层覆盖正是被它否定的做法。旧约束的具体成因我没有看到，只有结论。用户确认重做不受其限制，选择分层覆盖加追溯日志。

若实现后发现"某个值来自哪层"仍难排查，回退方案是改为显式引用（每个类型列出所用模块）。

## 影响

- 规则变更报告：旧仓库 AGENTS.md 要求每次规则变更单独报告。重做后是否沿用，待定。
- 追溯信息增加了 processed_data 的体积，量很小。
